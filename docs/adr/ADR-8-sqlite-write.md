# ADR-8: 主进程 SQLite 写策略（utilityProcess 托管写 + 事务粒度约束）

> 任务：T-M0-04（计划 todo 6，Spike S3）· 依据：04-架构评审报告.md:52-58（S3）、04:111（放行条件：M0 内出 spike 报告）、02-系统架构设计.md:699-718（§14.1 客户端 SQLite/WAL）、05:271（spike 风险行）
> 日期：2026-10-11 · 平台：Windows 11 · 状态：**已决（采纳）**
> 证据：`.omo/evidence/mvp0-dev-plan/task-6-mvp0-dev-plan.log`（命令+退出码+三轮完整数据）；复现沙箱 `bench/sqlite-write-bench/`
>
> **结论一句话**：T11 store 采用 **utilityProcess 托管写（唯一写者）+ worker 内事务批处理（≤100 行/事务）**；主进程不持常驻写连接，仅允许在窗口创建前执行一次性启动迁移（须显式 busy_timeout）。实测三方案在良性负载下同步阻塞全部达标，但人工锁库实验证明主进程直写在写锁竞争下必然停摆 2.26s（超红线 11 倍），只有托管写在同一实验中保住主进程（滞后 ≤13ms）——故按数据选 B。

## 1. 背景与问题（S3 全文摘要）

better-sqlite3 是同步 API；批量写入（采集落库 + 快照 + 日志 + 截图索引同事务）在 Electron 主进程执行时会阻塞 CDP 事件处理与 IPC 响应，表现为 UI 卡顿、拟人节奏抖动——节奏抖动是反爬敏感面（02 §7.1）。04:56 要求 M0 spike 实测两案：(a) store 迁入 `utilityProcess`/worker_threads，主进程只持异步代理；(b) 保留主进程但强制事务粒度约束（单事务 <16ms）+ 批量写队列化。以实测数据出本 ADR（04:57），结论写入 §4.2 store 条目（T11 执行）。

## 2. 判定标准（阈值框架先于填数固定）

以下四条为**预承诺判定框架**，来源逐条标注，实测数据（§4）填入后不改框架：

| # | 标准 | 阈值 | 来源 |
|---|---|---|---|
| T1 | 单次写操作在主进程造成的事件循环同步阻塞 **p95** | **≤ 50ms** 可接受；> 50ms 不可接受，须 utilityProcess 托管 | 05:59 任务卡预置（"如单次阻塞 p95 >50ms 不可接受"），本 ADR 固化为硬标准 |
| T2 | 单事务同步阻塞（C 方案调参目标线） | **< 16ms** | 04:56 方案 (b) 原文（"单事务 < 16ms"） |
| T3 | 任意单次写同步阻塞 max（可感知卡顿红线） | **≤ 200ms** | 本 ADR 固化（常规 UI 感知阈值量级；spike 内约定，非基线要求） |
| T4 | 写锁竞争下的有界性（failure QA 维度） | 阻塞时长必须**有界且显式**（显式设置 busy_timeout；无界等待禁止），竞争引发的阻塞计入 T1/T3 判定 | 04:56 "批量写队列化"的竞争面补全，本 ADR 固化 |

- 吞吐（ops/s）为**参考指标**，不作放行判定（基线未给客户端写吞吐硬指标；M3 容量压测 NFR-2 属 T-M3-07 范围）。
- 被评估为"可单独放行"的方案须同时满足 T1 + T3 + T4；T2 用于校准 C 方案的事务批次参数。
- 通过判定路径：逐条 hrtime 包裹写调用测同步段时长（A/C 直接测）；B 分开测主进程侧提交+await 时延与 worker 侧实写时长，另以 4ms 间隔事件循环滞后采样器（maxLoopLagMs）作旁证。

## 3. 实验设计

- **运行时**：全部场景在 **Electron 33.4.11 主进程 / utilityProcess** 下运行（结论效度要求；宿主 node v24.6.0 仅用于安装）。better-sqlite3 12.4.1 换装 electron-v130 预编译（镜像链路复用《sqlite-vec 打包验证》（M0 Spike S11，`docs/adr/sqlite-vec-packaging-validation.md`）的结论，换装后二进制 1,896,960 B 与该 ADR §4 记录一致）。
- **负载**：每轮 1000 行合成日志写入（模拟 02 §14.1 `logs` 表 8 列，行 ~250-350B），固定种子 20261011（mulberry32，载荷逐轮确定性生成）；**预热轮 1 轮不计入证据**，测 3 轮取稳定值；三次独立运行验证可重复性。
- **PRAGMA**：每轮新建 DB 文件，`journal_mode=WAL` + `synchronous=NORMAL`（02 §14.1）。
- **场景**：
  - **A 主进程直写**：逐条 autocommit INSERT（对照组）。
  - **B utilityProcess 托管写**：主进程 `utilityProcess.fork` 写 worker，经 MessagePortMain 逐条提交（串行请求-应答，M0 store 的现实异步模式）；主进程测提交+await 时延，worker 测 `stmt.run` 实写时长。
  - **C 事务粒度约束**：主进程直写，按 10/100/1000 行合并事务（tx=1 即 A 对照）。
- **failure QA（T4）**：另开连接 `BEGIN EXCLUSIVE` 持写锁不提交，再触发写，记录阻塞表现与错误；测 lockA（主进程直写，busy_timeout=2000 与 =0）与 lockB（写连接在 worker，主进程同期跑滞后采样器）。
- 环境：i7-9750H @2.60GHz / 31.9GB / Windows 11 10.0.26200 / Electron 内置 Node 20.18.3 / SQLite 3.50.4。

## 4. 实测数据

三次独立运行（run1/run2/run3，各 3 轮聚合；单位 ms；吞吐 ops/s）。逐轮明细见证据日志 §[4]/§[5]/§[7]。

### 4.1 三方案阻塞与吞吐（事件循环阻塞按 §2 口径）

| scenario | 口径 | p50 (r1/r2/r3) | p95 (r1/r2/r3) | max (r1/r2/r3) | 吞吐 (r1/r2/r3) |
|---|---|---|---|---|---|
| A 主进程直写（tx=1） | 逐条实阻塞 | 0.035 / 0.058 / 0.050 | **0.074 / 0.116 / 0.116** | 7.817 / 11.052 / 7.678 | 17,756 / 11,620 / 13,748 |
| C 主进程直写 tx=10 | 单事务阻塞段 | 0.087 / 0.164 / 0.094 | **0.205 / 0.320 / 0.172** | 0.582 / 0.836 / 0.260 | 94,616 / 55,118 / 94,654 |
| C tx=100 | 单事务阻塞段 | 0.430 / 0.585 / 0.540 | **0.848 / 0.850 / 0.704** | 1.025 / 0.994 / 1.045 | 214,197 / 172,273 / 194,488 |
| C tx=1000（单条大事务） | 单事务阻塞段 | 4.467 / 6.657 / 3.628 | **4.467 / 6.657 / 3.628** | 4.805 / 7.382 / 3.903 | 222,235 / 149,686 / 273,590 |
| B 主进程侧 | 提交+await 时延 | 0.240 / 0.266 / 0.222 | **0.504 / 0.520 / 0.401** | 8.413 / 25.171 / 6.958 | 3,400 / 3,159 / 3,776 |
| B worker 侧 | 实写时长 | 0.056 / 0.062 / 0.052 | 0.130 / 0.142 / 0.109 | 8.064 / 21.520 / 6.688 | 3,400 / 3,159 / 3,776 |
| C tx=10/100/1000 折算每行 | 摊销 | 0.003~0.016 | 0.004~0.032 | 0.004~0.084 | 同上 |

- A 的孤立 max 尖峰（6.5~11.1ms）与 B 的孤立 max（6.5~25.2ms）均为单样本离群点（WAL 边界/系统调度量级），p95 不受影响；B 主进程侧 maxLoopLagMs 采样 12~16ms（1000 条消息处理期），无 >50ms 事件。
- B 串行 IPC 吞吐 ~3.2-3.9k ops/s 为**串行逐条提交**的往返上限，非 worker 写能力上限（worker 侧实写 p95 0.13ms/条 ≈ A 量级；worker 内改批量事务后端到端吞吐逼近 C，见 §6）。

### 4.2 failure QA：人工锁库（三次运行一致）

| 场景 | 配置 | 实测阻塞 | 结果 |
|---|---|---|---|
| lockA-busy2000 | 主进程直写，外部连接 `BEGIN EXCLUSIVE` 持锁，busy_timeout=2000 | **2259.1 / 2268.7 / 2252.8ms** | ~busy_timeout 后抛 `SQLITE_BUSY: database is locked`；逐条 hrtime 测量捕获该 2.25-2.27s 阻塞（检测路径可触发✅）；**超 T3 红线（200ms）11 倍** |
| lockA-timeout0 | 同上，busy_timeout=0 | **0.053 / 0.050 / 0.053ms** | 即刻 `SQLITE_BUSY`（有界快速失败分支可用✅） |
| lockB-busy2000 | 写连接在 utilityProcess，同一持锁，busy_timeout=2000 | worker 侧 **2255.6 / 2252.8 / 2256.0ms**；主进程同期最大滞后 **12.86 / 12.74 / 12.73ms** | worker 被锁死 2.25s 期间主进程事件循环保持响应（隔离性实证✅） |

诚实注记：实测阻塞 2.26s 略超 busy_timeout 2000ms（~13% 开销，含锁等待重试与调度）；有界性成立，但量级本身即主进程不可接受。

## 5. 数据对照判定标准

| 方案 | T1（p95≤50ms） | T2（单事务<16ms） | T3（max≤200ms） | T4（锁竞争有界性） | 判定 |
|---|---|---|---|---|---|
| A 主进程直写 | ✅ 0.074~0.116ms | —（逐条） | ⚠️ 良性负载 ✅（max 6.5~11.1ms）；**锁竞争 ❌（2.25~2.27s）** | ❌ 无界风险（应用侧约束防不住外部锁竞争/checkpoint/其他进程） | 良性达标，竞争场景不可放行为常驻写路径 |
| C 主进程直写+事务约束 | ✅ ≤0.85ms（tx≤100）；tx=1000 亦 <16ms | ✅ tx=1000 最大 7.4ms | ⚠️ 同 A：良性 ✅，锁竞争 ❌（C 不改变持锁者仍是主进程） | ❌ 同 A（事务粒度约束是应用侧纪律，防不了外部竞争） | 同 A；可作 B 的 worker 内批处理参数 |
| B utilityProcess 托管写 | ✅ 主进程侧 0.401~0.520ms；隔离实验主进程滞后 ≤12.9ms | —（worker 内适用 C 参数） | ✅ 良性（max 6.5~25.2ms）与锁竞争（滞后 ≤12.9ms）双通过 | ✅ 竞争阻塞被隔离在 worker，主进程旁路无感 | **通过，选为主方案** |

关键结论：**在良性合成负载下，A/C 的同步阻塞数字全部达标（两个数量级余量）**——S3 担心的"正常写卡 UI"在 1000 行/轮、行 ~300B 的规模上不成立。但 T4 failure QA 揭示了 A/C 的结构性弱点：锁竞争（外部连接、WAL checkpoint、杀软扫描、未来多进程读）会把任意一条同步写放大成 ≥busy_timeout 的主进程停摆（实测 2.26s），事务粒度约束对此无防御；只有 B 把该停摆隔离出主进程。判定标准 T4 为区分性标准。

## 6. 选型结论

**采纳 B：utilityProcess 托管写（唯一写者），worker 内合并 C 事务批处理（默认 ≤100 行/事务或 <16ms，两者正交）。**

- 主进程只持异步代理（MessagePort 请求-应答），收益：锁竞争/大事务/长迁移不再停摆 UI 与 CDP 事件处理（S3 的核心关切按实测闭环）；代价：串行逐条吞吐 ~3.4k ops/s（M0 日志+任务落库足够），批量提交或 worker 内组事务可恢复吞吐（C 数据：tx=100 达 17-21 万行/s）。
- 主进程直写仅在两处允许：① app 启动、任何 BrowserWindow 创建前的**一次性迁移链**（此时无 UI 可卡，直写最简单，须显式 busy_timeout）；② 降级开关（见 D6）。
- D6 fallback 检查：预置分支"同步写超标且 utilityProcess 改造代价超预算时，仍锁定 utilityProcess 托管写并给改造清单"。实测同步写（良性负载）**未超标**，该分支的触发前提未成立；但选型仍落在托管写（依据 T4 区分性标准），改造代价经本 spike 验证可控——本沙箱即最小可用原型（写 worker 73 行、主进程消息代理约 40 行，协议含 id/错误回传），改造清单并入 §7。
- 本 ADR 为 04:57 要求的"结论写入 §4.2 store 条目"提供依据，T11 执行时在 02 §4.2 store 处回链本文件。

## 7. 给 T11 的实现约束（store/迁移链，todo 11 必须遵循）

1. **唯一写者**：SQLite 写连接收敛到一个 utilityProcess（写 worker）；主进程不持常驻写连接（启动迁移除外，见 §6）；渲染进程永不触碰 SQLite。读可经写 worker 或独立只读连接（WAL 允许并发读），M0 建议读也走 worker 以简化。
2. **事务批次上限**：worker 内单事务 ≤100 行**且**同步段 <16ms（T2 双上限，先到先提交）；禁止在事务内做 IPC/网络/用户交互等待（长事务 = 锁持有时间 = 竞争放大器，见 §4.2）。
3. **busy_timeout 显式设置**：写连接 `busy_timeout=2000`（不得依赖默认值、不得 0/无界）；worker 收到 `SQLITE_BUSY` 时向上回传错误并由应用层重试队列处理（busy_timeout=0 的即刻失败模式保留给要求快速失败的场景，如激活写入）。
4. **WAL 维护**：`journal_mode=WAL` + `synchronous=NORMAL`（02 §14.1）；写 worker 空闲期周期 `wal_checkpoint(TRUNCATE)`（如每 5 分钟或每 N 万行），降低 A 场景实测的 checkpoint 边界尖峰（7.8~11.1ms 量级）叠加到业务写上的概率。
5. **IPC 协议最低要求**：请求带自增 id、响应回传 `{id, writeMs, err}`、调用方超时（建议 5s）与错误回传不可省略——本 bench 的协议即最小实现（`bench/sqlite-write-bench/bench-worker.js`）；批量提交接口（`writeBatch`）随 T11 一起落，供日志五类流水与 task_events 批量写使用。
6. **背压与队列**：主进程侧异步写队列设 in-flight 上限（建议 ≤1000 条），超限触发丢弃/降级策略（日志类可丢，任务/授权类禁止丢）。
7. **启动迁移**：迁移链在 app ready 后、任何 BrowserWindow 创建前于主进程同步执行（一次性、无 UI 感知），或整体迁入写 worker——二选一由 T11 定；无论哪种，迁移事务同样受约束 2（分批 DDL/DML，单事务 <16ms 目标）。
8. **行宽与容量复测触发器**：本 bench 行宽 ~250-350B；M3 容量压测（T-M3-07，NFR-2：50 万笔记）前若单行均值 >2KB（截图索引/大 JSON 列），须以本 bench 重跑复核 C 批次参数与 checkpoint 周期。
9. **重跑义务**：Electron 大版本升级（ABI 变化，M5 自动更新前必经）与 macOS 首次打包时，重跑本 bench + S11 打包验证（S11 ADR §6 同款义务）；utilityProcess 在 Windows 下已实测可用（本证据），macOS 未测（S11 同款范围限制）。
