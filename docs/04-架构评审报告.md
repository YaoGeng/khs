## 2. 架构优点（予以确认，不在后续评审中重复）

1. **决策质量高**：ADR-1~6 均给出备选、否决理由与代价，无"只有结论没有理由"的选型；Electron + Playwright(connectOverCDP) + SQLite + NestJS 的技术组合与"Local-First、真实浏览器接管、密钥不出端"三大约束高度匹配。
2. **人机共驾落到了状态机**：humanGate 不是 UI 层的提示，而是任务状态机的一等状态（awaiting_user），确认动作幂等——这是本产品合规叙事的架构级兑现，设计到位。
3. **不可重入步骤的幂等设计**：发布/评论的"意图记录 + 恢复后先核对"直接支撑 NFR-3"零重复发布"，方案正确。
4. **平台适配层数据化 + 签名热更**：把"平台改版"从线上事故转化为可检测、可热修、可回滚的常规运维事件，是对最高风险 R1 的正确对冲；"不含可执行 JS"的安全边界声明尤其重要。
5. **熔断与遥测闭环**：熔断事件上报 → B 端聚类 → 远程下调配额/关停入口，与 PRD §5.7 应急预案形成工程闭环。
6. **服务端克制**：模块化单体 + Compose 起步、读多写少的配置/遥测先行拆分，扩展路线务实，没有过度设计。

## 3. 高等级问题

### S1（高）会员套餐缺"设备档"维度，授权链路无法按 PRD 实现

- **位置**：§14.2 `memberships.plan(month/quarter/year)`、`activation_cards.plan`、`licenses`、§12.3 JWT claims、§9.5 签发时序。
- **问题**：PRD 套餐 = 时长 × 设备档（个人 1 台 / 团队 3 台）共 6 个 SKU，但 schema 只建模了时长。§9.5"校验会员/设备数上限"的上限值没有数据来源，§6.1"激活设备数超限被阻断"验收不可执行。此问题即对齐报告 D-02。
- **建议**：`memberships` / `orders` / `activation_cards` 增加 `tier` 字段；许可证 JWT claims 增加 `device_limit`，签发时由 tier 映射；§12.3 同步。
- **验证时机**：M0 编码前（文档修订）；M0 门禁用"个人版第 2 台设备激活被阻断"用例验证。

### S2（高）崩溃恢复依赖"核对页面是否已成功"，但适配层 DSL 没有 verify 声明

- **位置**：§6.3 失败与补偿表第 4 行、§7.5 适配层结构、§9.3。
- **问题**：发布/评论等不可重入步骤在"已执行、未落 checkpoint"窗口崩溃时，恢复路径要求"先核对页面是否已成功（搜索草稿/评论列表）"。核对动作本身是页面交互，但适配层 DSL 当前只声明 `selectors` 与 `flows`，没有 `verify` 类步骤。若 DSL 不扩展，每个不可重入步骤的核对逻辑将散落为硬编码，违背"策略与执行分离"原则（§1.2-3），且热更无法覆盖。
- **建议**：适配层 DSL 增加 `verify` 声明（如 `publish.verify: 草稿箱存在含标题 X 的笔记` / `comment.verify: 评论区可见文本 Y`），与 `flows` 同级、同样签名热更；引擎对标记 `nonReentrant: true` 的步骤强制要求 verify 存在。
- **验证时机**：M2 前完成 DSL 规范修订；M3（发布工作流）编码时按新 DSL 开发，门禁用"发布中途 kill 进程，重启后零重复"用例验证。

## 4. 中等级问题

### S3（中）better-sqlite3 同步写可能阻塞主进程事件循环

- **位置**：§3.1（better-sqlite3）、§4.2 store、§6.1。
- **问题**：better-sqlite3 是同步 API；批量写入（如采集落库 + 快照 + 日志 + 截图索引同事务）在主进程执行时，会阻塞 CDP 事件处理与 IPC 响应，表现为 UI 卡顿、拟人节奏抖动——而节奏抖动恰是反爬敏感面（§7.1）。
- **建议**：M0 spike 实测两种方案：(a) store 模块迁入 `utilityProcess`/worker_threads，主进程只持异步代理；(b) 保留主进程但强制事务粒度约束（单事务 < 16ms）+ 批量写队列化。以实测数据出 ADR-8。
- **验证时机**：M0 spike（T-M0-04）；结论写入 §4.2 store 条目。

### S4（中）"主流程用结构化输出（JSON Schema）"对 OpenAI 兼容服务商的能力假设过强

- **位置**：§3.1 LLM 接入、§8.1 确定性护栏。
- **问题**：BYOK 意味着服务商不可控；`response_format: json_schema` 在 DeepSeek/通义/智谱/硅基流动等之间支持参差，部分仅支持 json_object 或完全不支持。架构虽已有"失败自动纠偏重试 2 次"，但缺**能力探测**环节，纠偏重试对"接口直接报错"类失败无效。
- **建议**：llm-gateway 增加 provider 能力探测（首次调用时探测 response_format/tool_call/嵌入接口支持度，结果缓存本地），按能力档位降级 schema 注入策略（原生 json_schema → prompt 内嵌 schema → 正则抽取兜底）；探测表纳入用量面板展示。
- **验证时机**：M0 spike 出探测矩阵（5 家预设服务商），M1 报告 Agent 按探测结果路由。

### S5（中）语义聚类的嵌入来源未决策，引入模型分发或接口兼容性风险

- **位置**：§8.2 report-agent 工具"本地嵌入聚类（BGE 类小模型本地推理或用户 LLM 嵌入接口）"。
- **问题**：二选一未决。本地模型路线引入：模型文件分发体积（数百 MB）、许可证合规、Electron 内推理性能；用户接口路线引入：嵌入接口兼容性（同 S4）与额外成本。此问题即对齐报告 B-5。
- **建议**：出 ADR-7——V1 默认走用户 LLM 嵌入接口（随 S4 能力探测），样本不足或接口不可用时降级为统计聚类（TF-IDF + 层次聚类，无外部依赖）；本地模型列二期。
- **验证时机**：M1 编码前。

### S6（中）CDP 调试口暴露面：127.0.0.1 + 随机端口不足以防本机恶意进程

- **位置**：§5.3 连接韧性、§11.2 调试口。
- **问题**：随机端口对本机恶意进程可枚举（读 DevToolsActivePort 或端口扫描），一旦连入调试口即可操控用户已登录会话——这是比"远程攻击者"更现实的威胁（用户环境不可控）。§5.3 已提"二期 pipe"，但 V1 没有缓解。
- **建议**：V1 两层缓解：(a) 启动后对调试端口的 WebSocket 握手校验来源 PID/进程路径，非本客户端派生进程即断连；(b) DevToolsActivePort 文件权限收紧 + 读取后立即接管并监听新连接。M0 spike 同步评估 Playwright 对 `--remote-debugging-pipe` 的支持成熟度，若可用则 V1 直接上 pipe，跳过端口方案。
- **验证时机**：M0 spike 出结论；安全测试在"缓冲与合规审查"阶段渗透测试项中覆盖。

### S7（中）服务端可用性与恢复目标未量化

- **位置**：§15.3、NFR-4（99.5% 月可用 ≈ 月停机 ≤ 3.6h）。
- **问题**：单机 Compose + 每日全量备份的组合，恢复时间（RTO）与恢复点（RPO）未定义；99.5% 的预算分解（部署停机、故障恢复、支付回调重放）缺失。单机"蓝绿可选"在单 VPS 上意义有限，属冗余表述。
- **建议**：明确 RTO ≤ 4h、RPO ≤ 24h，授权服务可用性单独计量（其宕机有客户端 72h 宽限兜底，实际用户影响低）；删除或限定"蓝绿"表述。
- **验证时机**：M5 部署演练（含一次恢复演练）验收。

## 6. 风险登记册评审意见（对 §17）

- R1（平台改版）：缓解措施充分，但建议补**量化 SLA 的监控口径**——"24h 响应"从"自检失败率告警触发"起算，而非用户投诉起算，需在 M1 遥测中实现该告警。
- R2（账号风控）：接受。补充建议：M4 推广上线前做一次**内部红队演练**（测试账号跑满默认配额一周，观察平台反应），作为 M4 门禁项。
- R4（会员破解）："接受单机可破的残余风险"的表述诚实且正确，无需追加投入。
- R5（LLM 成本失控）：单任务 ¥5 阈值建议改为**按套餐档差异化**（个人/团队），随 S1 的 tier 一并落地。
- 新增 R9（自 S4/S5）：**BYOK 服务商能力碎片化**——探测矩阵 + 降级链覆盖，M1 关闭。
